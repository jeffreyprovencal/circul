1. Verified context — what was checked before drafting
Per Soul + CTO standard, every claim the mockup rests on was verified against the live codebase before drafting. Anything not verified is labelled in §14.

Schema — migrations/1774500000000_restructure_tiers.js + follow-ups

  • collectors has: id, first_name, last_name, phone, pin VARCHAR(10), city, region, must_change_pin (added by 1776300000000_add_must_change_pin.sql), is_active.
  • aggregators has: id, name, phone, pin VARCHAR(10), city, region, is_active. Missing must_change_pin — confirmed via grep; new migration required.
  • agents (from 1776600000000_batch8b_and_batch9.js) has: id, aggregator_id, first_name, last_name, phone, pin TEXT, must_change_pin BOOLEAN DEFAULT false, city, region, is_active.
  • collectors.aggregator_id does NOT exist. The prior draft mockup's "SELECT a.phone FROM aggregators a JOIN collectors c ON c.aggregator_id = a.id" query would have failed at runtime. Correct lookup: most recent aggregator from transactions by transaction_date.
  • aggregators.pin is VARCHAR(10) — too small for scrypt salt:hex (~70+ chars). Must widen to VARCHAR(255) before any hashed PIN is written into it.

USSD dispatch — server.js:4255 (POST /api/ussd)

  • Phone-number lookup cascades: collectors → aggregators → agents → handleUnregisteredUssd. Matches are exclusive (first hit wins).
  • Each handler receives (parts, userRow). parts = text.split('*'), per AT USSD contract. Session state is implicit in the parts array; there is no separate state table (ussd_sessions is log-only).
  • Each of handleRegisteredUssd (server.js:2505), handleAggregatorUssd (server.js:2693), handleAgentUssd (server.js:3083) uses the same PIN-retry pattern: loop up to 3 parts, try each as a PIN via verifyPassword, fail after 3 with END Too many wrong PINs.

SMS helper — shared/notifications.js

  • Public API: notify(event, recipientPhone, data). Not sendSms(phone, message). Event-driven with registered TEMPLATES.
  • Africa's Talking provider via AT_API_KEY / AT_USERNAME / AT_SENDER (defaults to 'Circul', matching registered sender ID).
  • Per-phone daily cap: SMS_DAILY_CAP=20, enforced in-memory. Relevant for reset flow: if a user hit 20 notifications today on other events, a reset OTP would be cap-blocked. Mitigated by security-event bypass (§12).
  • Already imported + used at 14+ call sites in server.js — adding new events is a well-established pattern.

Admin UPDATE endpoints — server.js:5554 + server.js:5575

  • PUT /api/admin/aggregators/:id and PUT /api/admin/collectors/:id both accept phone as an updatable field. Gated by requireAdmin. Build dynamic SQL — phone-only update is valid.
  • No admin UI wires to these. admin.html is 437 lines with zero PUT calls or references to these endpoints. The endpoints are backend-only today.
  • No conflict check: unique index on collectors.phone / aggregators.phone / agents.phone means a collision returns a generic 500 with no user-friendly message. Implementation must add a pre-UPDATE SELECT across all three tables.
  • No admin_audit_log table exists anywhere. Must be created.

PIN policy — inconsistent

  • USSD registration (server.js:2414): 4–6 digits, numeric.
  • Web registration (server.js:290): 4–6 digits.
  • PATCH /api/collectors/:id/change-pin (server.js:336): exactly 4 digits.
  • Another path (server.js:6394): at least 4 digits.
  • Reset flow should settle on 4–6 digits numeric (matches USSD registration, most permissive while still constrained). Flagged as a parallel cleanup item — not blocking.
2. Security model
Feature-phone identity: the phone number IS the account. Same constraint as MTN MoMo, Vodafone Cash, Airtel Money. Defense-in-depth compensates where prevention can't prevent. Phone-change flow extends the model for the lost-phone case we couldn't close with OTP alone.

The four layers

  • 1. SMS OTP to phone — blocks remote-only attacks. 6-digit random, 10-min TTL, single-use, SHA-256 at rest, timing-safe comparison.
  • 2. Instant alert SMS to account holder — if someone else resets, you get an SMS as it happens. Visibility defense.
  • 3. Upstream-tier notification — collector reset alerts their most recent aggregator; aggregator reset alerts all processors they've transacted with; agent reset alerts their owning aggregator. Social + financial friction.
  • 4. Admin phone-change with OTP-to-new-number — for lost-phone (new number) cases. Admin initiates; OTP goes to the NEW number so we prove the user physically holds it before swapping. Parallel SMS to old number (if reachable) + upstream tier.

No post-reset transaction cooldown: Circul doesn't hold money on-account, so a "pause on logging drop-offs/purchases" would block legitimate users (who'd be unable to log their day's work after a legitimate reset) to prevent an attack that doesn't cash out in our model. If Circul ever adds on-account money, reintroduce the cooldown at that time.

10. Backend + data model
Complete inventory of new artifacts. Sign off on this before implementation so the migration sequencing in §11 holds.

New tables

  • pin_reset_codes — id SERIAL, phone VARCHAR(50) NOT NULL, user_type VARCHAR(20) NOT NULL CHECK (user_type IN ('collector','aggregator','agent')), user_id INTEGER NOT NULL, code_hash VARCHAR(64) NOT NULL (SHA-256 hex), expires_at TIMESTAMPTZ NOT NULL, used_at TIMESTAMPTZ, attempts_remaining SMALLINT NOT NULL DEFAULT 3, created_at TIMESTAMPTZ DEFAULT NOW(). Partial unique index: CREATE UNIQUE INDEX pin_reset_codes_active ON pin_reset_codes (phone) WHERE used_at IS NULL AND expires_at > NOW() — one active code per phone at a time.
  • phone_change_codes — same shape as above, but new_phone VARCHAR(50) NOT NULL column added. OTP goes to the new number. On success, admin flow commits: update {user_type}.phone = new_phone, mark used_at = NOW(), write admin_audit_log row.
  • user_lockouts — id SERIAL, user_type VARCHAR(20) NOT NULL, user_id INTEGER NOT NULL, phone VARCHAR(50) NOT NULL, locked_until TIMESTAMPTZ NOT NULL, reason VARCHAR(50) NOT NULL ('wrong_pin_x3' | 'wrong_otp_x3'), created_at TIMESTAMPTZ DEFAULT NOW(). Index on (phone, locked_until). Checked by USSD dispatch before handler routing; if locked, return END with unlock time.
  • admin_audit_log — id SERIAL, actor_type VARCHAR(20) ('admin' | 'aggregator' | 'processor'), actor_id INTEGER, actor_email VARCHAR(255), action VARCHAR(50) (e.g. 'phone_changed', 'pin_reset_triggered', 'user_flagged'), target_type VARCHAR(20), target_id INTEGER, details JSONB, created_at TIMESTAMPTZ DEFAULT NOW(). Indexes on (actor_id, created_at) and (target_type, target_id, created_at).

Column additions

  • aggregators.must_change_pin BOOLEAN DEFAULT false — parity with collectors and agents. Used by admin-initiated PIN reset.
  • aggregators.pin widened: ALTER TABLE aggregators ALTER COLUMN pin TYPE VARCHAR(255). Required for scrypt hash storage.

Notifications — new events in shared/notifications.js

  • PIN_RESET_OTP — to user's own phone; body includes 6-digit code + 10-min TTL.
  • PIN_RESET_COMPLETED — to user's own phone; confirms reset with "if this wasn't you, call" escalation.
  • PIN_RESET_UPSTREAM_ALERT — to upstream tier; per-role body (aggregator gets "collector PIN reset", processor gets "aggregator PIN reset", aggregator gets "agent PIN reset").
  • PHONE_CHANGED_NEW — to new phone.
  • PHONE_CHANGED_OLD — to old phone (best-effort).
  • PHONE_CHANGED_UPSTREAM_ALERT — to upstream tier.
  • ADMIN_PIN_RESET_TRIGGERED — to user's own phone when admin sets must_change_pin=true.

USSD handler changes — server.js

  • Dispatch addition (/api/ussd around line 4260): before the role-cascade lookup, check user_lockouts by phone. If locked, return END Account locked until HH:MM. Then check pin_reset_codes by phone for an active reset — if found, route to handleForgotPinUssd(parts, row) regardless of role.
  • New handler: handleForgotPinUssd(parts, resetRow) — covers Screens C8–C13 (OTP entry, wrong OTP, new PIN, confirm, success). On success: hash new PIN with scrypt, UPDATE {user_type} SET pin=$1, must_change_pin=false WHERE id=$2, mark used_at=NOW(), fire PIN_RESET_COMPLETED + PIN_RESET_UPSTREAM_ALERT.
  • Welcome-screen updates: handleRegisteredUssd:2506, handleAggregatorUssd:2694, handleAgentUssd:3084 — add "0. Forgot PIN" to welcome + wrong-PIN retry screens. If parts[0] === '0' at depth 0, route to the reset-request flow (Screens C6–C7 etc.).
  • Lockout write: in each handler's 3rd-wrong-PIN branch, insert into user_lockouts with locked_until = NOW() + INTERVAL '30 minutes' before returning END.

New endpoints — server.js

  • POST /api/admin/users/:type/:id/change-phone-start — body: { new_phone }. Validates format, checks cross-table uniqueness (SELECT from collectors, aggregators, agents — return 409 on collision). Creates phone_change_codes row, calls notify(PHONE_CHANGE_OTP, new_phone, { code }). Returns { success: true, code_id }.
  • POST /api/admin/users/:type/:id/change-phone-confirm — body: { code_id, code }. Timing-safe compare against code_hash. On success: UPDATE phone in the correct table, mark code used, fire 3 SMSes, write admin_audit_log.
  • POST /api/admin/users/:type/:id/reset-pin — sets must_change_pin = true, fires ADMIN_PIN_RESET_TRIGGERED SMS, writes audit row. User must complete reset via USSD self-serve.
  • GET /api/admin/audit-log — paginated listing, filterable by actor / target / action / date.
  • (Deferred) POST /api/aggregators/:id/collectors/:colId/change-phone-* — aggregator-initiated variant. Out of scope for this ship.

Security properties

  • OTPs: 6-digit random via crypto.randomInt(100000, 999999). SHA-256 hashed at rest. Plaintext only in SMS body. 10-min TTL. 3 attempts, then row invalidated. Timing-safe string comparison on entry (crypto.timingSafeEqual).
  • Rate limit: max 3 reset codes per phone per 24h (pin_reset_codes) and 3 phone-change codes per target user per 24h (phone_change_codes).
  • Single-use: UPDATE ... SET used_at = NOW() in same transaction as the PIN/phone write. Retry would see used_at IS NOT NULL and fail.
  • Scrypt for new PIN via the existing hashPassword helper (same path as USSD registration at server.js:2416).
  • All admin mutations write to admin_audit_log. No silent writes.

12. Security-event SMS cap bypass
Locked in: option #2. Security-critical notifications bypass the 20/day per-phone cap.

Implementation in shared/notifications.js

Add a named set of events that skip the bucket check:

var SECURITY_EVENTS = new Set([
  EVENTS.PIN_RESET_OTP,
  EVENTS.PIN_RESET_COMPLETED,
  EVENTS.PIN_RESET_UPSTREAM_ALERT,
  EVENTS.PHONE_CHANGED_NEW,
  EVENTS.PHONE_CHANGED_OLD,
  EVENTS.PHONE_CHANGED_UPSTREAM_ALERT,
  EVENTS.PHONE_CHANGE_OTP,
  EVENTS.ADMIN_PIN_RESET_TRIGGERED
]);

// Inside notify(), before the cap check:
if (provider === 'africastalking') {
  if (!SECURITY_EVENTS.has(event)) {
    // ... existing cap check ...
  }
  // ... send ...
}

Security events still count toward AT wallet consumption and Sentry logs, just not the per-phone daily cap. No double-counting or special telemetry needed — keeps the change surgical.

13. Trust-model disclosure
Communicate the trust model so users understand what protects them and what doesn't. Ship on onboarding welcome + marketing page.
Your Circul account

Your phone number is your Circul identity. We use SMS one-time codes to protect your account, but anyone with access to your SIM can receive these codes.

Protect your account:
• Use a PIN you can remember but others wouldn't guess (not 0000, 1234, your birth year).
• If you lose your phone, call Circul support or your aggregator immediately so we can freeze your account.
• If you get an unexpected "PIN reset" or "phone change" SMS, someone else tried to change your account — call support now.

If you lose your phone entirely and get a new number:
Contact Circul support. We can move your history to your new number after verifying who you are. Your transactions, ratings, and passport are kept on your account, not on your phone.

Your aggregator is notified every time your PIN is reset or your phone number is changed. They can flag suspicious activity and withhold payouts until resolved.
