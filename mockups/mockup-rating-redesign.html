Rating UX Redesign
Transaction-specific ratings · Photo upload · Persistent pill fix · ID verification moved to Profile
Summary of Changes

1 Transaction-specific ratings

Ratings are now tied to individual completed transactions, not partner-level. Each transaction row gets a "Rate" button. The modal shows transaction context (material, weight, date) so the user knows exactly what they're rating.

2 Pill fixes (count + dismiss)

The pill shows the exact count of unrated transactions. After rating, the count decrements in real time. At 0, the pill disappears entirely. No more stuck "success" state.

3 Photo upload in ratings

New optional photo section in the rating modal. Lets users document material quality, contamination, or delivery condition. Photos stored as URLs in a new rating_photos column.

4 ID verification stays in Profile

Ghana Card input lives exclusively in the Profile section — never in the Ratings tab. Clean separation: identity = Profile, feedback = Ratings.

Technical implementation notes

Database: No schema change needed. The ratings table already has transaction_id as a foreign key. Add photo_urls TEXT[] DEFAULT '{}' column to ratings table for photos.


API: /api/ratings/pending already returns transaction-specific data (transaction_id, material, weight, peer name). The Ratings tab just needs to render it as a table instead of a partner list.


Photo upload: Reuse the existing aggregator photo upload pattern (<input type="file" accept="image/*">). Convert to base64 or upload to server, store URLs in rating_photos column. Max 3 photos, 5 MB each.


Pill behavior: After submitRating() succeeds, immediately call checkPendingRatings(). Remove the "success" state entirely — the pill is either counting unrated transactions or hidden.


Applies to all buyer dashboards: Recycler, Processor, Converter (rate their sellers). Collector and Aggregator already have similar patterns. Unified approach across all 5 dashboards.
