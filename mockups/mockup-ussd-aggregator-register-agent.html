1. Strategic context
"I think we should have agents set their own PINs. How do we do that?" + "CTO and soul-standard all the way!" — Jojo, 2026-04-25

The original PR scope was USSD parity for agent registration. Verifying the must_change_pin flow surfaced a deeper gap: the column is set, the web client probably enforces it, but the USSD login flows do NOT. That means every collector registered via PR #65 today can dial in with PIN 0000 forever. Latent shipped-today security gap.

Soul-standard read: ship the policy fix and the new feature together. Building the USSD force-change-PIN gate just for agents and not for collectors/aggregators would mean the gap stays open for every user already in the system. One shared helper, three call sites, closes the gap universally.

Coupling rationale

  • USSD force-change-PIN gate is a shared helper. Once built, calling it from the agent login is one line. Calling it from collector + aggregator login is one line each. Trivial reuse, large security improvement.
  • Web POST /api/agents needs the same policy: drop PIN from input, set defaults, agent picks at first login. Otherwise web-registered agents have aggregator-known PINs forever and USSD-registered agents don't — bad data model.
  • USSD register-agent flow (the originally-scoped change) is the new feature. Without #1 and #2 it'd ship with the same latent issue we're fixing for collectors.

What works

  • USSD register-collector (PR #65) sets must_change_pin = true at INSERT (server.js:4663, 4712).

  • Cleared correctly in three places: change-PIN endpoint (server.js:363), Forgot PIN reset (server.js:3221), admin-initiated reset (server.js:7134).
  • Web login response includes the flag: must_change_pin: !!c.must_change_pin (server.js:6626). Client side (web aggregator-dashboard / collector-dashboard / etc.) presumably enforces a change-PIN modal.

Gap: USSD does NOT enforce must_change_pin

Read at server.js:3376 (handleRegisteredUssd for collectors), server.js:3206 (handleAggregatorUssd), and the agent login handler. Pattern in all three:

  1. Welcome + PIN prompt
  2. Validate PIN against scrypt hash
  3. Lockout after 3 wrong PINs
  4. Drop straight into the role's main menu

No must_change_pin check. The flag is set in the database but never gated on USSD login. Every USSD-registered user today (collectors via PR #65, future agents) gets to use the platform with their default 0000 PIN indefinitely.

Existing infrastructure we reuse

  • The change-PIN UPDATE pattern at server.js:3221 (UPDATE ${userTable} SET pin = $1, must_change_pin = false WHERE id = $2) — exactly what the new gate calls after a successful change.
  • hashPassword() for new PIN hashing.
  • verifyPassword() for PIN entry validation (already used in login flows).

Platform vocabulary alignment (callout)

The gate's three screens reuse existing platform vocabulary deliberately:

  • G1 body = verbatim from server.js:3195 (Forgot-PIN reset entry).
  • G2 = verbatim from server.js:3204 (Forgot-PIN reset confirm).
  • G3 body line "Use this PIN next time you log in" = NEW, but applied to BOTH the gate AND the existing Forgot-PIN reset success screen (server.js:3240) so the platform speaks one voice for "you just changed/set your PIN" moments.

All three screens render identically regardless of role (collector / aggregator / agent). The shared helper passes the same return strings; only the post-bridge route to the role's main menu differs.

Helper signature

async function gateForceChangePin(m, user, userTable) {
  // m = parts.slice(pinIndex + 1) — what's after the valid PIN
  // user = fetched row with must_change_pin field
  // userTable = 'collectors' | 'aggregators' | 'agents'
  //
  // Returns: { needsGate, response, menuParts }
  //   needsGate: true if caller should return `response` directly
  //   response: USSD response while in the change-PIN flow (or after)
  //   menuParts: defined when needsGate=false; the offset slice for main-menu use
}

Each role's login handler calls this immediately after PIN validation, before its existing const m = parts.slice(pinIndex + 1) menu logic. If needsGate is true, return the response. Otherwise use menuParts instead of m as the input to the existing menu logic.

Depth math (the tricky part)

USSD callbacks replay the full input history. Within the gate's lifetime, m contains:

  • m[0] = new PIN
  • m[1] = confirmation PIN
  • m[2] = bridge response (1 continue / 0 exit)
  • m[3+] = main menu navigation (after bridge=1)

After successful change, must_change_pin is FALSE in the DB. Subsequent callbacks within the same session re-fetch user → must_change_pin = false → gate returns immediately with menuParts = m.slice(3). The role's existing main-menu logic sees menuParts as if it had been the depth-0 input.

Important: the gate must return menuParts = m.slice(3) ONLY when both (a) the change has been committed AND (b) the bridge response was 1. The simplest implementation: gate inspects m, finds the change sequence at [0,1,2], and slices accordingly. If the user has not yet completed all three steps, gate is still active and returns its own response.

Validation + edge cases

  • Invalid new PIN format (not 4-6 digits): END PIN must be 4-6 digits.\nDial *920*54# to retry.
  • Mismatch on confirm: END PINs don't match.\nDial *920*54# to retry.
  • User picks 0 at the bridge: END Done. Dial *920*54# again to use the platform.
  • User typed default 0000 as new PIN: validation passes (0000 is 4 digits). Allowed but should we discourage? My read: don't discourage; it's their PIN to pick. Adding an "easy PIN" warning is post-pilot scope.
  • Mid-flow drop: USSD session ends, no commit happened, next dial starts gate from depth 0. Safe.

8. Edge cases

Existing agents (must_change_pin = false)

Existing agent rows have must_change_pin = false by default (column added via migration with that default). Their aggregator-set PINs continue to work. No forced change. They opt in via the existing change-PIN flow if they want.

Should we backfill existing agents to must_change_pin = true? No. Backfilling would force every existing agent to change PIN on next login — disruptive for users mid-pilot. The new policy applies to agents going forward; legacy agents stay on their existing setup until they Forgot-PIN-reset or change voluntarily.

Existing collectors registered via PR #65 today

These rows have must_change_pin = true ALREADY. Once the gate ships, their next USSD dial intercepts and forces a change. That's the intended behavior — they were always supposed to change, the platform just wasn't enforcing it. This fixes a shipped-today gap retroactively.

User picks "0. Exit" at the bridge (G3)

END Done. Dial *920*54# again to use the platform. Their PIN change is committed (between G2 confirm and G3 bridge), so they can now log in fresh with their new PIN.

Race: user changes PIN via two devices simultaneously

Highly unlikely in pilot. If it happens, both UPDATEs commit; the second one wins. must_change_pin is false in either case. No data integrity issue.

User locked out before reaching the gate

Gate runs AFTER PIN validation. If user fails 3 PIN attempts, lockout fires before the gate. Gate is never reached. After lockout, Forgot-PIN reset routes through the existing reset flow, which sets a new PIN and clears must_change_pin. Gate doesn't fire on the next login. Correct.

10. Locked decisions
  • Force-change-PIN gate is universal — fires on any USSD login where must_change_pin = true, for all three roles (collector / aggregator / agent). Closes the latent gap shipped with PR #65 retroactively.
  • Web parity — agent registration via web also drops the PIN field. Bootstrap PIN 0000, force-change at first login. Consistent across web and USSD.
  • Bootstrap PIN is 0000. Aggregator tells agent verbally; agent forced to change immediately. No SMS to the agent.
  • Aggregator menu refactor — top-level 1 becomes "Register" sub-menu (Collector / Agent). Replaces PR #65's "Register Collector" top-level slot.
  • USSD register-agent flow is 6 screens (not 7) — no PIN-entry step.
  • Audit trail — agent_activity with action_type='registered', description distinguishes USSD vs web via suffix.
  • No backfill for existing agents — must_change_pin stays false on legacy rows.
  • Bridge after successful change — 1. Continue / 0. Exit rather than END-and-redial. Lower friction.
  • Edge: 0000 as new PIN. Allowed (it's their PIN). No "easy PIN" warning pre-pilot.
  • Gate copy is role-agnostic. G1 / G2 / G3 render identically for collectors, aggregators, and agents. Shared helper, single source of truth.
  • Platform vocabulary alignment. G1 body = verbatim from Forgot-PIN reset entry (server.js:3195). G2 = verbatim from Forgot-PIN reset confirm (server.js:3204). G3 body line `"Use this PIN next time you log in."` is new, applied to BOTH the gate AND the Forgot-PIN reset success screen (server.js:3240 updated as part of this PR).
  • Collector-registration success screen updated for accuracy: `"They'll be asked to set their own PIN at first use."` (replaces `"Ask them to change their PIN on first use."` which implied voluntary). Applies to both aggregator-registers-collector (server.js:4674) and agent-registers-collector (server.js:4723).
