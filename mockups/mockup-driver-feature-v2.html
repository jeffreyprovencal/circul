D. Dispatch acceptance — direct invites + marketplace listings
Every dispatch requires explicit driver acceptance before it locks. Two paths to discovery: (1) direct invite — aggregator picks a specific driver from their roster; (2) marketplace listing — aggregator posts an open need to the regional pool. Both paths end with the driver accepting, countering, or declining. No driver is ever dispatched without consent.

Single dispatch lifecycle

created → pending_driver_accept → accepted (in-flight) → picked_up → delivered → paid

If driver declines OR doesn't respond within the listing TTL (24h for marketplace, 4h default for direct invites — configurable per aggregator), dispatch returns to created and aggregator gets re-notified to pick another driver or post to marketplace.

E. Confirm delivery — single weight input
The data integrity flow, simplified after design review. Driver enters one number at delivery: the accepted weight (what the buyer is paying for). System computes rejected. Weighbridge slip can be photo-uploaded later via web (optional evidence layer, not required for the field flow).

The simplified weighbridge model — workshopped 2026-05-07 PM

Drivers' incentive is to move material, get paid, move on. Anything beyond a single numeric input increases risk they bail mid-flow OR enter garbage to get past it. So we simplified.

Always captured at delivery:

  • pickup_weight_kg — already on pending_transactions (aggregator's claim at origin)
  • accepted_weight_kg — NEW. What buyer paid for. Driver enters this.

System derives:

  • Total delta = pickup − accepted (the commercial truth, basis for payment reconciliation)

Per-delivery delta is informational only. The difference could be transit loss, scale calibration drift, or quality rejection — we can't disambiguate without a weighbridge slip, and we don't try to. Trust signal lives in the aggregate: rolling avg total-delta % per processor over many deliveries reveals patterns. Consistent high delta with one processor = ask questions.

Optional weighbridge evidence: driver can photo-upload weighbridge slip via web (Section H) post-delivery. When attached, aggregator can manually inspect to separate transit loss from buyer rejection. Not required for the field flow.

G. Mutual ratings — platform-wide UI migration
After each delivery confirmed, both sides get a rating prompt at their next interaction. 4-point star scale (2-5), no free-text comments in v0. Average rating shown per actor + per relationship.

Why this is a platform-wide rewrite, not just a driver feature

The existing rating UI (handleUssdRating, server.js line 3520) used by collector, aggregator, and agent today has two latent bugs:

  • Unicode ★ chars force UCS-2 encoding — drops cap from 182 to 70 chars per page. On long peer names the screen exceeds 70 chars and AT can reject as malformed body.
  • 5 numbered options + 0 cancel = 6 menu items, exceeds the 4 + 0 Yam-phone rule documented in feedback_ussd_design_rules.md. Likely truncates on Yam phones, just hasn't been smoked.

Driver feature scope absorbs the migration. Single replacement screen template, applied to all four call sites (collector / aggregator / agent / driver). ~50 LOC delta.

The new compliant template:

  • 4 numbered options (2-5 stars) + 0 skip = 4 + 0 compliant
  • ASCII text "stars" instead of Unicode ★ — back to GSM-7, full 182 char cap
  • 1-star option dropped on USSD (rare in practice, can still be given on web). Web UI continues to support 1-5 full range; existing 1-star ratings stay valid.

K. Out of scope (and where each goes)

v1 enhancements (3-6 weeks post-v0 ship)

  • Photo upload of weighbridge slip — evidence layer for delta tracking
  • Weighbridge source picker (buyer site / commercial / other) — weights deltas by trust level
  • In-app messaging per dispatch — structured notes between aggregator and driver
  • Free-text rating comments — needs moderation pipeline
  • Driver self-deactivate / change phone — currently aggregator-mediated

v2 / never

  • Route optimization — needs real GPS, marginal value vs cost in informal sector
  • Money transfer — violates Circul's no-money-handling principle

NEVER (architectural boundary)

Drivers will never pick up directly from collectors. That's the boundary captured in project_circul_drivers_dont_aggregate.md. If a future feature would require it, escalate to a strategy conversation, not a feature decision.
