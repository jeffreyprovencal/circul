Aggregator Reports — Sourcing + Sales

Two parallel reports an aggregator can generate over any window, exportable as CSV + PDF. Sourcing (collectors → aggregator) is the brand-tier feature: Coke and similar require it as a precondition for purchasing. Sales (aggregator → processor / recycler / converter) is the aggregator's own statement to send their downstream buyers. Same UI shape, same component, same export pipeline — different SQL slice + different copy. Per project_circul_work_call_insights.md: pull-adoption, not push.

1. Why this — strategic context
"Coke can only buy from aggregators who can generate reports."
— WORK call insight, 2026-04-24

The brand-tier ask isn't "nicer dashboards" — it's required reporting infrastructure. Brand sustainability leads need an audit-grade record of what aggregators sourced (chain back to identifiable collectors) before purchasing. Once Circul is the supplier of that record, brand-tier customers route through us by necessity. Pull-adoption.

Two reports, one system

  • Sourcing report (primary, brand-tier-facing): "What I sourced from collectors during this window." Total sourced kg, total paid out, % from registered collectors, audit-grade per-transaction list. This is the Coke-onboarding lever.
  • Sales report (secondary, statement-style): "What I sold to a buyer during this window." Total volume, total value, traceability split, per-transaction list. Aggregator's own record-keeping; can be sent as a settlement statement to a processor / recycler / converter.

Both share a single backend endpoint per type, a single client component, a single PDF template (A4 landscape), and a single CSV emitter. Naming and labels flip based on report type via a type prop.

2. Privacy rule — collector identity in exports

HARD RULE — load-bearing

Per platform privacy policy ("Notes on Circul" + project_circul_dropdowns.md-era guidance): collector names NEVER appear in any generated report (PDF or CSV). Only collector ID codes (COL-0026). This rule is non-negotiable and applies to all current and future report types.

  • R1 filter dropdown: shows name-first with ID in parens (e.g. Ama Mensah (COL-0026)) for the aggregator's own selection convenience. This is UI, not export.
  • R2 on-screen preview: shows ID only — same as the export, so what you see is what you ship.
  • R3 PDF: ID only.
  • CSV: ID only. No collector_name column.
  • Sourcing scope: SQL filter collector_id IS NOT NULL — every Sourcing row is a registered collector by construction. Walk-in / declared-stock rows live on the Sales side only.

If implementation introduces a name field in any export by accident, the implementation is wrong and must be reverted.

3. Verified context

Existing PDF export pattern (template to model on)

Aggregator dashboard already ships a P&L PDF export via jsPDF + jsPDF-autoTable. Same library, same client-side render path, same Blob-download trigger. Reports reuse this pipeline — no new client deps. Orientation switches via new jsPDF('l', 'mm', 'a4') for landscape.

Transaction data already in place

  • pending_transactions with transaction_type discriminator: collector_sale (collector → aggregator), aggregator_purchase (aggregator's purchase ledger view), aggregator_sale (aggregator → processor/recycler/converter).
  • Source attribution: pending_transaction_sources junction table, live since PR3.
  • Form column (loose / baled) shipped in PR #59.
  • Payment status: 3-state — pending / payment_sent / paid. Cash-on-spot path direct to paid (server.js:4232).
  • Aggregator naming: COALESCE(a.company, a.name) pattern (server.js:5291).

Aggregator dashboard section structure

Reports lands as a new <div class="section" id="reportsCard"> placed near the bottom of the flow (after Marketplace + Transactions, before Profile). The Sourcing/Sales toggle is internal to that section.

7. Backend

Endpoint shape

  • GET /api/aggregator/reports/sourcing — sourcing report data.
  • GET /api/aggregator/reports/sales — sales report data.

requireAuth + role check (req.user.hasRole('aggregator')). Query params: from, to, materials (CSV string, optional, default = all), collector_id (sourcing only, optional, default = all), buyer_kind + buyer_id (sales only, optional, default = all). Response: { success: true, summary: {...}, rows: [...], materials_present: [...] } — the materials_present array drives the PDF meta-line "Materials: PET, HDPE" rendering.

Sourcing SQL (sketch — to be verified during prompt drafting)

SELECT
  pt.id,
  pt.created_at AS date,
  'TXN-' || TO_CHAR(pt.created_at, 'YYYYMMDD') || '-' || LPAD(pt.id::text, 4, '0') AS ref,
  pt.collector_id,
  'COL-' || LPAD(pt.collector_id::text, 4, '0') AS collector_code,
  pt.material_type,
  pt.form,
  pt.gross_weight_kg,
  pt.net_weight_kg,
  pt.price_per_kg,
  pt.total_price,
  pt.payment_status,
  pt.payment_completed_at AS paid_at
FROM pending_transactions pt
WHERE pt.transaction_type IN ('collector_sale', 'aggregator_purchase')
  AND pt.aggregator_id = $1
  AND pt.collector_id IS NOT NULL    -- registered-only filter, hard rule
  AND pt.created_at >= $2 AND pt.created_at < $3
  AND ($4::text IS NULL OR pt.material_type = ANY(string_to_array($4, ',')))
  AND ($5::int IS NULL OR pt.collector_id = $5)
ORDER BY pt.created_at DESC

Notes: (1) SQL does NOT join the collectors table — names must never enter the response payload. (2) collector_id IS NOT NULL filter enforces the registered-only rule at the data layer — walk-in / declared-stock rows are excluded by definition. (3) The summary card "Largest Supplier" is computed in JS from the result set: GROUP BY collector_code, MAX kg.

Client-side rendering

  • Preview (R2): client renders summary + first ~5 rows.
  • CSV: client builds CSV string from response, triggers Blob download.
  • PDF: client uses jsPDF landscape mode ('l' orientation) + jsPDF-autoTable.

No new tables

Generate-on-demand. No aggregator_reports_generated table. Re-evaluate post-pilot.

8. Locked decisions
  • Both reports ship pre-holiday — same PR, one component, two SQL slices.
  • Toggle naming: Sourcing | Sales. Parallel, brand-tier-readable.
  • Storage: generate-on-demand only.
  • Privacy (HARD RULE): collector names NEVER in any export — PDF or CSV. IDs only. Names visible in R1 dropdown UI for selection only.
  • Sourcing scope = 100% registered. SQL filter collector_id IS NOT NULL excludes walk-in / declared-stock rows. No "Registered %" metric needed — it's always 100% by construction.
  • Sourcing 4th summary card: Largest Supplier (anonymized to COL-XXXX in the report). Surfaces supplier concentration as a self-improvement signal.
  • Sales scope keeps Traced/Declared split. The chain-of-custody attribution metric is meaningful precisely because it's honest about gaps. Asymmetric with sourcing is intentional — see project_circul_chain_of_custody_status.md for the PR3-vs-PR#59 history.
  • Traceability calc (sales): weight-weighted % of kg traced via pending_transaction_sources back to a registered collector.
  • Default filters: All collectors / All buyers, All materials, year-to-date.
  • Aggregator name on PDF: COALESCE(a.company, a.name).
  • PDF orientation: A4 landscape for both reports.
  • PDF header: title left, aggregator (company/name) top-right, single-line meta listing actual materials, "Generated…" on its own line.
  • Materials in meta: list actual materials present (e.g. "PET, HDPE") — never the word "All."
  • Form column: in CSV always; dropped from R2 preview + R3 PDF for fit.
  • Sourcing report: registered-only at SQL layer. No walk-in rows, no Source/Walk-in pill needed. Sales report keeps the Traced/Declared pill (chain-of-custody attribution metric).
  • Wordmark: text-only "Circul" below title.
  • Audit contact: hello@circul.app (forward-compatible).
  • Date format: DD/MM/YYYY in PDF (Ghana convention, full year for export clarity); ISO YYYY-MM-DD in CSV (machine-readable).
9. Verified vs Assumed

Verified against current main (prod tip 02d162b)

  • Aggregator dashboard ships jsPDF + jsPDF-autoTable for the existing expense PDF export. Landscape mode is a 1-line constructor change.
  • Tab pattern: .tab.on active-state class (PR #62 unified).
  • Aggregator naming: aggregators.company + aggregators.name both exist; COALESCE(a.company, a.name) at server.js:5291.
  • Payment states: 3-state on both transactions and pending_transactions (server.js:4232 / 5977 / 6011).
  • Form column shipped in PR #59 on pending_transactions.
  • Chain-of-custody junction (pending_transaction_sources) live since PR3.
  • Privacy rule in memory (Notes on Circul + dropdowns guidance): collector names NEVER in exports.

Assumed (verify during implementation prompt drafting)

  • collector_sale vs aggregator_purchase overlap. Both transaction types appear at insert sites (server.js:3167 / 3384 / 3619 / 4030 / 5390 / 7907). Need to verify whether the same logical event lands as both rows (would double-count) or if they're disjoint slices. Resolve via grep + insert-path review during prompt drafting.
  • Walk-in collector modeling (Sales side, not Sourcing). The chain-of-custody attribution metric for Sales reports counts source rows where collector_id IS NOT NULL as "traced" and ones where it's NULL as "declared". Verified at server.js:3619 — declared-stock rows are aggregator_purchase with collector_id: null, source: 'ussd_declared'. This modeling is correct.
  • Reports section placement. Lands as <div class="section" id="reportsCard"> in the aggregator dashboard's long-scroll flow. Suggested position: after Transactions, before Profile. Confirm during implementation.
  • jsPDF-autoTable column-fit at A4 landscape. 9 columns + landscape should fit comfortably; verify with a render pass on the first implementation.

Could be wrong if

  • The aggregator_purchase / collector_sale overlap is non-trivial — sourcing SQL would need a deduplication step.
  • Brand-tier reviewers want traced_pct calculated differently. Revisit if the first brand-tier buyer pushes back.
  • Collectors want to be NAMED on reports they're proud to be associated with. Counter to current privacy rule; would require explicit opt-in mechanism, post-pilot signal.
