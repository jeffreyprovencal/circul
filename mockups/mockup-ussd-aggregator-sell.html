2. Scope + rationale
Why this, why now, what's in and out.

Why now

  • USSD went live on prod 2026-04-24 (97 sessions / 11 Ghana phones dialed in, demo-mode). The aggregator channel that was planned post-CoC-series is now the natural next build — memory project_circul_ussd_aggregator_sell has been the holding design.
  • BanQu trial learning: aggregators without smartphones were the bottleneck. A USSD-only aggregator should be able to do BOTH purchase (from collector) AND sale (to processor/recycler/converter) without ever touching a web dashboard. This ships the second half of that story.
  • Pilot-readiness for Pat Mensah / WORK partnership demo — a complete aggregator workflow on USSD is more compelling than a half-workflow.

In scope

  • Menu rename: "Log Purchase" → "Log Transaction", add direction sub-screen.
  • Existing Purchase flow is preserved exactly — accessed via direction=1. Zero behavior change on that path.
  • New Sale flow (direction=2): material → form (loose/bale) → weight → declare-shortfall prompt if weight > tracked inventory → buyer → confirm → auto-attribute + write aggregator_sale pending_transaction.
  • Declared-stock support — if the aggregator wants to sell more than they have tracked via collector_sale transactions, they can declare the shortfall as existing stock inline during the sale. Backend creates a root transactions row with collector_id = NULL to represent aggregator-declared (untraced) inventory. Unblocks day-one pilot adoption for aggregators with pre-existing material.
  • Buyer discovery shows processors + recyclers + converters via posted_prices in the aggregator's region, sorted by price.
  • Confirmation screen shows the traced/declared split so aggregators see their traceability mix — organic pressure over time to onboard their collectors to improve traced%.
  • Standard USSD end-screens with contact details (buyer's phone + city).

Out of scope for this PR

  • Per-bale weight capture. Decision (2026-04-20): just capture total weight, form toggle is informational only.
  • Manual source picking for the sell side. FIFO auto-attribute is the only path; USSD users don't see attribution. Web source-selector UI (PR4/5/6) stays the advanced path for aggregators who want manual control.
  • Offering / counter-offering via USSD on the sell side. Marketplace existing functionality on the menu stays browse-only for now.

What changed from the first draft

The earlier version of this section had a "Screen E2 · over-inventory" that END'd the session with "Weight exceeds inventory. Dial again and enter a lower weight." That error path is now the primary happy-path for the common case of aggregators with pre-existing stock (handled via S3.5a/b in §5). The end-state was wrong: a real aggregator with 1500kg to sell but only 1240kg tracked would have been forced to either lie about the weight or abandon the flow. Kept the other edge cases (no buyers, invalid input) as real ENDs.

Race: two concurrent sales drain the same inventory

Aggregator dials from two phones, both submit 800kg of PET against a 1000kg inventory simultaneously. Possible because inventory check runs at Screen S3 (pre-confirm) but attribution runs at Screen S6 (commit). Between those, another session could have committed.

Mitigation: attributeAndInsert re-checks inventory inside its transaction and throws InsufficientSourceError (which handleInsufficientSource at server.js:41 already handles for the web path). On USSD, wrap the commit in try/catch and return END Inventory changed, try again on that error. Graceful degradation, no data corruption. Note: the declare-shortfall path sidesteps this race entirely when invoked — since declared stock is always sufficient for the requested sale, there's no source to race over.

Inventory query (used in Screens S1 + S3 validation)

Mirrors the exact filter attributeAndInsert uses internally when FIFO-walking aggregator sources — so what the user sees matches what the backend will attribute. The remaining_kg column is pre-decremented by the helper on each sale, so it's the source of truth; no subquery subtracting consumed rows is needed.

SELECT material_type,
       COALESCE(SUM(remaining_kg), 0) AS available_kg
  FROM pending_transactions
 WHERE aggregator_id = $1
   AND transaction_type IN ('collector_sale', 'aggregator_purchase')
   AND remaining_kg > 0
   AND created_at >= NOW() - INTERVAL '30 days'
   AND status NOT IN ('rejected', 'dispatch_rejected', 'grade_c_flagged')
 GROUP BY material_type

The 30-day window. attributeAndInsert enforces a freshness constraint on source material per shared/chain-of-custody-db.js. Bundled with this PR: expand WINDOW_DAYS from 14 to 30. Rationale: pilot-scale aggregators consolidate for multiple weeks before selling upstream; 14 days pushed too much material into the declare path. 30 days keeps typical collection cycles inside the tracked window. Chain-of-custody freshness claim weakens slightly — revisit when a real brand-tier buyer sets an expectation. Aggregators who hold material longer than 30 days can still sell it via the declare-shortfall path (§5).

Buyer-discovery query (Screen S4)

SELECT pp.poster_type, pp.poster_id, pp.price_per_kg_ghs,
       CASE pp.poster_type
         WHEN 'processor' THEN (SELECT company FROM processors WHERE id = pp.poster_id)
         WHEN 'recycler'  THEN (SELECT company FROM recyclers  WHERE id = pp.poster_id)
         WHEN 'converter' THEN (SELECT company FROM converters WHERE id = pp.poster_id)
       END AS name,
       CASE pp.poster_type
         WHEN 'processor' THEN (SELECT phone FROM processors WHERE id = pp.poster_id)
         WHEN 'recycler'  THEN (SELECT phone FROM recyclers  WHERE id = pp.poster_id)
         WHEN 'converter' THEN (SELECT phone FROM converters WHERE id = pp.poster_id)
       END AS phone,
       CASE pp.poster_type
         WHEN 'processor' THEN (SELECT city FROM processors WHERE id = pp.poster_id)
         WHEN 'recycler'  THEN (SELECT city FROM recyclers  WHERE id = pp.poster_id)
         WHEN 'converter' THEN (SELECT city FROM converters WHERE id = pp.poster_id)
       END AS city
FROM posted_prices pp
WHERE pp.material_type = $1
  AND pp.is_active = true
  AND pp.poster_type IN ('processor','recycler','converter')
  AND (pp.region = $2 OR pp.region IS NULL)
ORDER BY pp.price_per_kg_ghs DESC
LIMIT 4 OFFSET $3

recyclers table verified to exist (migration 1774800, used 14+ places in server.js including GET /api/recyclers at server.js:2090). Query shape is correct.

Bale vs loose — where to store

  • Current pending_transactions schema has no form column. Options:
  • (a) Append to notes field as "form: baled". Zero migration. Weak queryability later.
  • (b) Add form VARCHAR(10) CHECK (form IN ('loose','baled')) column via new migration. Clean. Usable in processor dashboards later.
  • Recommend (b) — form affects downstream processing (baled → less sorting), so processors will want to filter by it. One-column migration, idempotent, low risk.

Aggregator-declared stock — schema design (corrected after verification pass)

The entire chain-of-custody ledger lives in pending_transactions, not transactions. Root rows (collector_sale, aggregator_purchase) and downstream rows (aggregator_sale, processor_sale, recycler_sale) all share this one table. attributeAndInsert FIFO-walks it, insertRootTransaction inserts to it. The transactions table exists but isn't part of the chain-of-custody flow — declared stock has no business there.

  • Storage: declared stock is a root pending_transactions row with transaction_type = 'aggregator_purchase' (existing root type, parentType-eligible for aggregator-seller attribution per candidateFilterForSeller), collector_id = NULL, aggregator_id = X. pending_transactions.collector_id is already nullable per migration 1774500 (ON DELETE SET NULL) — no schema change needed.
  • Status: 'confirmed' (skips the drop-off-confirmation limbo that 'pending' carries). Keeps declared rows out of aggregator "Pending Drop-offs" lists that filter on status = 'pending' at server.js:4705. Confirmed by EXCLUDED_STATUSES in shared/chain-of-custody.js:59 — 'confirmed' is attribution-eligible.
  • Write path: if declared > 0, inside the same DB transaction as the sale:
    1. insertRootTransaction(client, { transaction_type: 'aggregator_purchase', aggregator_id, collector_id: null, material_type, gross_weight_kg: declared, net_weight_kg: declared, price_per_kg: 0, total_price: 0, status: 'confirmed', source: 'ussd_declared' })
    2. attributeAndInsert(client, { transaction_type: 'aggregator_sale', aggregator_id, processor_id | recycler_id | converter_id, material_type, gross_weight_kg: total_sale_weight, price_per_kg, total_price })
    The helper FIFO-consumes across all in-window aggregator sources (older collector_sale rows first, then the newly-inserted declared row if needed). Same transaction, atomic.
  • 30-day window bypass: declared rows enter with created_at = NOW(), so they're always in-window. Aggregators with >30-day-old tracked material can effectively "refresh" it by declaring the equivalent amount — by design. The untraced label downstream is the accountability.
  • Downstream visibility: /api/trace/:batch_id (server.js:6374) walks pending_transaction_sources and renders every ancestor. Rows with collector_id IS NULL render without a collector name; the trace page needs a small conditional to show "Aggregator-declared origin (untraced)" for those rows. Low-impact UI change.
  • Aggregator "Pending Drop-offs" list: at server.js:4705 filters on status = 'pending', so declared rows (status 'confirmed') won't pollute it. Verified. At server.js:4750, a separate query filters collector_id IS NOT NULL for a confirmed-drop-offs display — declared rows won't appear there either. Verified.

Migration summary

  • ALTER TABLE pending_transactions ADD COLUMN form VARCHAR(10) CHECK (form IN ('loose','baled')) — bale-vs-loose capture (nullable default; old rows stay NULL).
  • No schema change for declared stock. The earlier draft of this mockup proposed DROP NOT NULL on transactions.collector_id; that was based on a wrong assumption about where aggregator inventory lives. pending_transactions.collector_id was already nullable — nothing to migrate.
  • The aggregator_sale and aggregator_purchase transaction_types are already in the pending_transactions.transaction_type CHECK per 1774500. No change there.
  • Total: 1 small migration.

Remaining assumptions

  • Region-fallback policy for buyer discovery. My recommendation: if a material has no regional buyers, fall back to country-wide. The mockup currently shows local-only + "try Marketplace" as the empty state. Decide before implementation — small UX call, backend supports either.
  • Trace page behavior for NULL-collector rows. /api/trace/:batch_id walks every ancestor; the page render at public/trace.html probably uses collector_display_name and similar fields. Needs a small conditional to render "Aggregator-declared (untraced)" when the chain row's actor resolver returns null (i.e., aggregator-owned root with no collector). I'll read public/trace.html + the _traceActorFor helper in the Claude Code prompt-drafting step and specify the exact change.
  • Price on declared row. Mockup recommends zero. Alternative: use the sale price as a proxy (so downstream "value in chain" math doesn't see a zero-value ancestor). Zero is simpler and clearly an audit signal "no purchase happened through Circul." Lock this at implementation time.

Could still be wrong if

  • The form toggle needs to be per-collection rather than per-sale-batch, if processors require knowing form of the original collection. Unlikely given the data flows downstream and aggregators bale after they collect.
  • The trace page has rendering logic that breaks on NULL collector_id beyond just missing display names (e.g., null-dereferences an actor object). Worth grepping public/trace.html before drafting the Claude Code prompt so the UI change can be scoped accurately.
