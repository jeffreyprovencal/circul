USSD Aggregator Registration

Request-first-then-code flow: aggregator candidate (or WORK staff on the ground) dials USSD, selects "Register as Aggregator," provides name + company + city, which creates a pending_aggregator_registration row. Admin is notified, reviews in dashboard, approves or rejects. On approve, a 6-digit code is SMS'd; candidate re-dials, enters code, sets PIN, registration completes. Replaces the design in project_circul_role_fraud_prevention.md which assumed code-first (not feasible for Ghana's field reality per the BanQu lesson + 2026-04-24 Jojo correction). Coexists with peer-invite as a future extension.

2. Security model
The feature is a trust gate on who joins the aggregator tier. Three layers of defense.

The three layers

  • 1. Human-in-the-loop approval — admin reviews every incoming request before a code is issued. Admin has context (WORK staff intro? Existing relationship? Anomalous request?) that automation doesn't. Admin decides if this candidate belongs on the aggregator tier.
  • 2. Code-confirms-phone-possession — after admin approves, the 6-digit code is SMS'd to the candidate's claimed phone. Candidate must enter the code on USSD to complete registration. Proves the candidate holds the SIM they provided during the request step. Same mechanic as PIN reset in PR #58; reuse the helpers.
  • 3. Audit log — every approval, rejection, and completed registration writes to admin_audit_log. If a rogue aggregator shows up later, the chain (request created when, approved by whom, code issued when, registration completed when) is visible.

What this does NOT defend against

  • Approved-candidate turns-out-bad. Admin approves in good faith; candidate later engages in fraud. Defense lives in behavioral detection (flag aggregators with anomalous patterns — never buying from collectors, never selling upstream) + ratings system. Those exist or are scoped elsewhere; this PR doesn't own them.
  • SIM-swap between approval and code-entry. Small window (10-min code TTL), SIM-swap is a multi-hour operation at minimum. Not a realistic threat at pilot scale.
  • Collusion between admin and candidate. Audit log is the forensic layer. If Jojo approves his cousin's fake aggregator, the log shows it. Social/institutional deterrent, not technical.

Rate limiting

  • Per-phone: max 1 active pending request at a time. If a request is pending, the same phone can't create a second one until the first is resolved (approved/rejected/expired).
  • Per-phone: max 3 requests per phone per 24h (catches "admin rejects, candidate immediately re-requests" loops — same 3/24h cap as PIN reset from PR #58).
  • Code TTL: 10 min. Code attempt limit: 3 wrong entries burns the code; candidate has to request again.

Race: admin approves while candidate is in-flight

Candidate submits request, immediately dials again to see status. Admin approves in between. If we route based solely on "pending" vs "code_issued" status, the candidate dialing at an unusual moment could bypass the code-entry screen and land in the fresh welcome.

Mitigation: dispatch check is strict — "active request for this phone with status IN (pending, code_issued)" routes to the appropriate screen. Pending → "Request already pending" END (screen R6). Code_issued → code-entry screen (C1). Only after registration completes (status=completed) does the welcome re-appear, and by then they're a registered aggregator so they hit the aggregator welcome anyway.

Race: code entered while admin is still approving

Not possible by construction — the code is only generated at approval time. Before approval, no code exists in the DB, candidate has nothing to enter. Dispatch sees status=pending → screen R6.

10. Backend + data model

New table: aggregator_registration_requests

One row per request. Status transitions: pending → code_issued → completed OR pending → rejected OR code_issued → expired/code_failed.

CREATE TABLE aggregator_registration_requests (
  id                     SERIAL PRIMARY KEY,
  phone                  VARCHAR(50) NOT NULL,
  name                   VARCHAR(255) NOT NULL,
  company                VARCHAR(255),
  city                   VARCHAR(100) NOT NULL,
  region                 VARCHAR(100),
  country                VARCHAR(100) DEFAULT 'Ghana',
  status                 VARCHAR(20) NOT NULL DEFAULT 'pending'
                         CHECK (status IN ('pending','code_issued','completed','rejected','expired','code_failed')),
  code_hash              VARCHAR(64),         -- SHA-256 of the 6-digit, null until approval
  code_expires_at        TIMESTAMPTZ,         -- null until approval; approval sets NOW() + 10 min
  code_attempts_remaining SMALLINT DEFAULT 3,
  approved_by_admin_email VARCHAR(255),       -- null until approved
  approved_at            TIMESTAMPTZ,
  rejected_by_admin_email VARCHAR(255),       -- null until rejected
  rejected_at            TIMESTAMPTZ,
  rejection_reason       TEXT,                -- mandatory on reject; SMS'd to candidate
  aggregator_id          INTEGER REFERENCES aggregators(id) ON DELETE SET NULL,  -- null until completed
  source                 VARCHAR(20) DEFAULT 'ussd',
  created_at             TIMESTAMPTZ DEFAULT NOW(),
  updated_at             TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_agg_reg_phone ON aggregator_registration_requests (phone);
CREATE INDEX idx_agg_reg_status ON aggregator_registration_requests (status);
CREATE INDEX idx_agg_reg_created ON aggregator_registration_requests (created_at DESC);
-- Partial unique index: one active (pending or code_issued) request per phone at a time
CREATE UNIQUE INDEX idx_agg_reg_active
  ON aggregator_registration_requests (phone)
  WHERE status IN ('pending', 'code_issued');

USSD handler changes

  • Dispatch update at /api/ussd (server.js; grep for location): before the user-lockout check, add an active-aggregator-registration-request check. If a row exists with status IN ('pending', 'code_issued'), route to the appropriate handler.
  • New handler handleAggregatorRegistrationCode(parts, requestRow) — handles Screens C1-C4 (code entry, PIN, confirm, complete). Uses verifyOtp from PR #58 for code validation. On success: BEGIN, INSERT aggregator, UPDATE request row status=completed + aggregator_id, COMMIT. Fire completion SMSes (candidate + admin) non-blocking.
  • Welcome copy update: handleUnregisteredUssd depth-0 branch now returns the role-split screen (Screen W1). The collector path (parts[0] === '1') stays as-is. Aggregator path (parts[0] === '2') routes to handleAggregatorRegistrationRequest(parts.slice(1), phone).
  • New handler handleAggregatorRegistrationRequest(parts, phone) — Screens R1-R5, E1-E4. Pre-flight checks (already-aggregator, already-pending, rate-limit). Collects name / company / city / confirm. On submit: INSERT into aggregator_registration_requests with status=pending, fire admin notification, END with success message.

New admin endpoints

  • GET /api/admin/aggregator-requests — list pending + recent (configurable via ?status= query). Returns requests with name, company, city, phone, created_at, status. requireAdmin-gated.
  • POST /api/admin/aggregator-requests/:id/approve — transitions status pending → code_issued. Generates OTP, hashes, stores, sets expires_at, SMSes candidate via AGGREGATOR_CODE_ISSUED, writes admin_audit_log row. Returns { success: true, code_id: N }.
  • POST /api/admin/aggregator-requests/:id/reject — body { reason } required. Transitions pending → rejected. Stores reason. SMSes candidate via AGGREGATOR_REQUEST_REJECTED. Writes admin_audit_log row.
  • (Deferred) POST /api/admin/aggregator-requests/:id/re-approve — for code_failed/expired states, generate new code. Out of MVP scope.

New notification events in shared/notifications.js

  • AGGREGATOR_REQUEST_RECEIVED → admin (ntfy primary + Ghana SMS fallback); body includes candidate name + company + city + phone + admin URL. See §10.3 below for dual-channel wiring.
  • AGGREGATOR_CODE_ISSUED → candidate phone; 6-digit code + 10-min TTL + "never share." Added to SECURITY_EVENTS set (cap bypass).
  • AGGREGATOR_REQUEST_REJECTED → candidate phone; rejection reason + support contact.
  • AGGREGATOR_REGISTRATION_COMPLETED → new aggregator phone; welcome message.

Admin notification dual-channel — ntfy.sh primary + Ghana SMS fallback

ntfy.sh is already used for error-spike alerts (server.js:7235, env var NTFY_TOPIC). Reuse the pattern with a new topic for admin alerts.

  • New env var NTFY_ADMIN_TOPIC — Jojo subscribes to this topic on his ntfy mobile app. Default fallback: circul-admin-alerts.
  • New env var ADMIN_ALERT_PHONE — Jojo's Ghana number (0207973412) for SMS fallback.
  • New helper in shared/notifications.js: notifyAdmin(event, data) — fires both channels in parallel via Promise.allSettled. Each channel logs independently if it fails; no exception propagates.
  • Ntfy POST: fetch('https://ntfy.sh/' + process.env.NTFY_ADMIN_TOPIC, { method: 'POST', body: messageText, headers: { 'Title': event, 'Priority': 'default', 'Tags': 'building' } }). No API key needed; topics are effectively shared-secret URLs.
  • SMS fallback: existing notify(event, process.env.ADMIN_ALERT_PHONE, data) path.
  • Either channel can be disabled by leaving the corresponding env var unset. If both are unset, log a warning — no admin alerts will fire.

Why dual-channel: ntfy works internationally (Jojo is often in Bristol) and is free; SMS is guaranteed delivery but domestic only. Together: Jojo gets a near-instant push even in Bristol; if he's on the road without ntfy/data, the Ghana SMS still reaches him whenever he has reception.

Security + integrity properties

  • Codes: 6-digit random via crypto.randomInt(100000, 1000000). SHA-256 at rest. Plaintext only in the SMS body. Timing-safe compare on entry (crypto.timingSafeEqual, reused from PR #58).
  • Rate limit: max 3 requests per phone per 24h. Max 1 active (pending or code_issued) request per phone at a time (enforced by partial unique index).
  • Code TTL: 10 minutes. 3 attempt limit. Burned on success OR on 3rd wrong attempt. Timed expiry (status=expired) if not used by expires_at.
  • Cross-table phone uniqueness: at request-create time, SELECT across collectors, aggregators, agents to prevent registering a phone already in use. Per-role END messages (Screen E4).
  • Audit: every admin action writes to admin_audit_log with action IN ('aggregator_request_approved', 'aggregator_request_rejected', 'aggregator_registration_completed'). Completion audit is system-authored (actor_type='system') — candidate completed, not an admin mutation.

Concurrent-admin race

Two admins open the same pending request, both click Approve. POST /approve uses UPDATE ... SET status='code_issued' ... WHERE status='pending' — first-write-wins semantics. Second admin's request returns 409 Conflict with current status. UI refreshes queue on error, second admin sees the request now in code_issued state.

12. Deferred scope (future iterations)

Peer-invite path (processor / aggregator approves)

The original project_circul_role_fraud_prevention.md had processors and existing aggregators issuing codes. This is still worth building, but not in this MVP. Adds: permission system (who can approve), per-role invite-issuance UI, separate code-issuance endpoint. Holds until we see pilot demand signal for "my processor already knows me, why does Circul support need to re-approve?"

Re-approve for expired / code-failed requests

If a code expires or burns through 3 attempts, admin currently has to reject and the candidate re-requests. Adds one fetch-and-regenerate endpoint. Saves one admin step; low priority until real operational signal.

USSD aggregator sell-upstream integration with declared-stock flow

PR #59's aggregator-sell flow has a declare-shortfall path for untraced inventory. Newly-registered aggregators will have zero inventory, so their first sale will hit the declare path. That's working as designed — no change needed — but worth naming as an expected interaction.

City expansion beyond pilot 4

USSD city picker is hardcoded to 4 cities (Accra / Kumasi / Tamale / Takoradi). Expansion to more cities is post-pilot scope; add to USSD_CITIES constant when geographic footprint grows. Memory project_circul_stakeholders.md — events like GHNPAP June/July 2026 may surface new cities.
