USSD Expansion
Discovery Marketplace + Collector Selling + Aggregator Buying & Selling via USSD
New USSD Flows

1 Collector: Sell Material

Post listings, view/accept offers from aggregators. Browse aggregator buy requests. Contact details shared on acceptance via USSD screen + SMS.

2 Collector: Discovery

Browse aggregator buy requests by material. Respond with "I have this material" to send your details to the buyer.

3 Aggregator: Browse & Buy

Browse collector sell listings, make offers, post buy requests. Contact details shared on acceptance.

4 Aggregator: Sell to Buyer

Aggregators can sell upstream to processors, recyclers, and converters via USSD — avoiding the smartphone bottleneck (learned from BanQu trial).

Key Design Decisions

Contact details on every acceptance screen: When an offer is accepted or a "I can supply" response is sent, both the USSD screen and the SMS notification include the other party's phone number and location. This is how the deal moves from digital to physical — they call each other to arrange drop-off/collection. Mirrors how informal waste trading already works in Ghana.


Aggregator sells upstream via USSD: BanQu trial showed aggregators without smartphones become a bottleneck. This flow lets aggregators post sell listings and respond to processor/recycler/converter buy requests entirely from a feature phone. Includes grade selection (Clean/Mixed) since upstream buyers care about quality.


No counter-offers on USSD: The web app supports 2-round negotiation (offer → counter → accept). On USSD, we simplify to accept/decline only. Counter-offers require too many screen transitions within the 180-second timeout. If someone wants to negotiate, they decline and the other party can submit a new offer — or they call each other directly using the contact details.


SMS notifications bridge the gap: When a listing is posted, relevant parties in the area get an SMS. When an offer is made or accepted, both parties get SMS with contact details. USSD sessions stay short — users dial back in only when they have something to act on.


Privacy rules preserved: Collector listings show COL-XXXX IDs, not real names — consistent with web adjacency privacy rules. Aggregator and buyer-tier listings show business names since they're registered businesses. Phone numbers only shared after an explicit accept/respond action.


Location from registration, not per-session: Uses the user's registered location (city/region) for filtering and display. No need to ask location each time — saves screens within the 180-second timeout.


7-day expiry, auto-cleanup: Listings expire after 7 days, same as web. Users can renew via USSD (My Listings → select → Renew). Expired listings are filtered out of browse results.


Same API endpoints: All new USSD flows hit the existing listings/offers API (/api/listings, /api/offers). No new database tables needed — the USSD handler just translates menu inputs into the same HTTP calls the web dashboards make.


Session state encoding: Discovery flows add depth levels but stay within the stateless text field pattern. Example: "3*1*2*500*1*4.50*1" = Sell to Buyer → Post Listing → HDPE → 500kg → Clean → 4.50/kg → Confirm. No Redis needed.

Implementation Summary

New USSD handler files:

ussd/menus/collector-discovery.js — Browse buyers, respond to requests

ussd/menus/collector-sell.js — Post listing, manage listings, view offers

ussd/menus/aggregator-discovery.js — Browse sellers, post buy request, manage offers

ussd/menus/aggregator-sell.js — Post sell listing to processors/recyclers/converters, browse buyer requests, manage received offers


Modified files:

ussd/handler.js — Route new menu options to new handler files

ussd/menus/collector.js — Updated main menu (add options 2 + 3)

ussd/menus/aggregator.js — Updated main menu (add options 2 + 3)

ussd/sms.js — SMS notification templates with contact details on accept/respond


Existing API reuse:

POST /api/listings — create listing (collector sell, aggregator buy/sell requests)

GET /api/listings — search with material + location + listing_type filters

POST /api/offers — make offer on listing

PATCH /api/offers/:id — accept/decline (no counter on USSD)

GET /api/offers/mine — check sent/received offers


No new tables or schema changes. Discovery and sell-to-buyer reuse the existing listings and offers tables. The listing_type field distinguishes sell vs. buy listings. USSD is just a new interface to existing business logic.


Estimated effort: ~5-6 additional days on top of the base USSD build (which was ~1 week). Total USSD build with Discovery + Sell to Buyer: ~2.5 weeks development.
