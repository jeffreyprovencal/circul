1. Why this — strategic context
"Aggregators have to be able to register collectors via USSD flow. We've just seen why. Neither agents, nor aggregators or collectors will predominantly using smartphones." — Jojo, 2026-04-25

The Sourcing report's strategic story (Coke / brand-tier supplier verification) requires every collector who supplies an aggregator to be registered on Circul. The platform must give feature-phone aggregators a low-friction path to register — directly, without going through an agent or web dashboard. This is the missing pre-req for the "100% registered" claim.

Two paths, one goal

  • Top-level path (Register Collector menu item #1): for batch onboarding. Aggregator dials in on a Sunday morning before market day and registers all the collectors they expect to buy from that week.
  • Inline path (at point-of-purchase): when an aggregator is logging a purchase and the collector's phone doesn't match a registered collector, prompt to register on the spot. Strategic enforcer: there's no path to log a purchase from an unregistered seller — registration becomes a side-effect of buying.

Both paths reuse the existing handleAgentRegister data shape (server.js:3918) — same fields, same INSERT, same default PIN, same audit pattern.

2. Verified context — agent register flow as template

Existing agent register-collector flow (server.js:3918)

The agent USSD has had a battle-tested register-collector flow since the agent feature shipped. The aggregator version mirrors it.

  • Top-level path (no pre-fill): first_name → last_name → phone → city → confirm → INSERT.
  • Inline path (phone pre-filled from purchase flow): first_name → last_name → city → confirm → INSERT. Skips phone entry because the phone is already known from the parent context.
  • INSERT shape: collectors (first_name, last_name, phone, pin, city, region, must_change_pin) with default PIN '0000' (scrypt-hashed) and must_change_pin = true. The collector gets a default PIN they're forced to change on first login.
  • Phone normalization: normalizeGhanaPhone() converts 0207973412 ↔ +233207973412. Stored in 0XXX format.
  • Duplicate handling: unique constraint on collectors.phone (errcode 23505) → END "This phone number is already registered."
  • Audit: agent flow logs to agent_activity with action_type = 'registered_collector'. Aggregator flow needs an equivalent audit trail (see §7).

USSD city picker (paginated)

Per PR #63, USSD has a USSD_CITIES_LIST at server.js:2417 with 8 pilot regional capitals (Accra, Kumasi, Tamale, Takoradi, Cape Coast, Koforidua, Ho, Sunyani), paginated 3 per page. Reuse this picker exactly. Don't introduce a new city list.

SMS to the new collector?

Today's agent register-collector flow does NOT SMS the new collector. The aggregator tells them their default PIN verbally / in-person. We follow the same pattern — no SMS on registration. (Adding it would be cheap but post-pilot scope; the aggregator-collector relationship is in-person.)

5. Inline registration at point-of-purchase
When an aggregator is logging a purchase and the entered phone doesn't match a registered collector, prompt to register inline. Eliminates the "go register them first, then come back" friction. Strategic enforcer — every purchase ends up with a registered collector.

*920*54#Log Transaction
CON Buy from collector Enter collector's phone number: (e.g. 0207973412)
B1 · existing purchase flow (unchanged)
User types phone and presses Send.
→
*920*54#Not registered
CON 0207973412 is not registered on Circul. Register them now to log this purchase? 1. Yes, register 0. Cancel
B2 · NEW — register-or-cancel prompt
Replaces today's behavior (which is "Collector not found, dial again"). The aggregator can't proceed with this purchase without registering the collector first — but registration is one tap away.
→
*920*54#Register · step 1
CON Enter collector's first name:
B3 · enter first name (phone pre-filled)
Phone is carried forward from B1, so the inline path skips phone entry. From here, the flow is: first name → last name → city → confirm → register-and-return.
*920*54#Register · success → continue
CON Ama Mensah registered! PIN: 0000 (tell them to change on first use) Continue purchase: 1. Yes, log purchase 0. Done for now
B7 · NEW — bridge back to purchase
After registration, prompt to continue the purchase. Picking 1 drops back into the existing Log Transaction flow with the new collector pre-selected (jumps straight to material picker). Picking 0 ENDs.
→
*920*54#Log Transaction
CON Select material: 1. PET 2. HDPE 3. LDPE 4. PP
B8 · existing material picker (unchanged)
From here the existing purchase flow proceeds: material → weight → price → confirm. No further changes needed downstream.

Why the bridge-back screen (B7)?

Without it, the aggregator finishes registration → END. Then they have to dial *920*54# again, navigate back to Log Transaction → Buy from collector → re-enter the phone. Three extra screens of friction at the worst possible moment. The bridge keeps the aggregator in the original purchase intent.

6. Edge cases

Already-registered phone (top-level)

At A6 confirm, INSERT raises errcode 23505 (unique constraint on phone). End screen:

END This phone number is
already registered.

Use Log Transaction to
record purchases from
existing collectors.

Mirrors agent flow at server.js:4309 / 4358 verbatim.

Already-registered phone (inline)

This case shouldn't happen — B2 only fires if the phone WAS NOT registered. But defensive: if a TOCTOU race somehow collides (two aggregators registering the same phone at the same instant), the second's INSERT raises 23505, fall through to:

END This collector was
just registered by
someone else.

Dial *920*54# again
to log your purchase.

Invalid phone format

If normalizeGhanaPhone() returns null (not a valid Ghana mobile), END with "Invalid phone number. Dial again to retry." Mirrors today's USSD validation pattern.

Aggregator hits "0. Cancel" mid-flow

At any depth, 0 exits to "END Cancelled." No partial state persisted. Standard USSD pattern.

Aggregator typing whitespace-only first/last name

Trim before INSERT. If empty after trim, END with "Name cannot be empty. Dial again to retry."

7. Backend + audit trail

Where the code lands

  • Menu reshape (server.js:3242 in handleAggregatorUssd): change main-menu return string + add branches for 1 (Register Collector) and 4 (More sub-menu). Marketplace + My Stats moves into the 4 sub-handler — internal logic unchanged.
  • New top-level register handler: handleAggregatorRegister(parts, aggregator, prefilledPhone) — new function next to handleAggregatorUssd. Mirrors handleAgentRegister at server.js:3918 line-for-line, with the audit-log change noted below.
  • Inline register branch: in the existing aggregator purchase flow (around server.js:3380 — handleAggregatorPurchase or similar), when the entered phone doesn't match a registered collector, return the B2 prompt. On 1, route into handleAggregatorRegister with the entered phone pre-filled. On register success, return the B7 bridge prompt. On 1 from B7, drop back into the purchase flow with the new collector_id.

Audit trail

Today's agent flow logs to agent_activity with action_type = 'registered_collector'. Aggregator-direct registration has no equivalent table. Two options:

  • Option 1 (recommended): reuse admin_audit_log with actor_type = 'aggregator'. The audit log is generic enough to hold this. Action: 'aggregator_registered_collector', target_type: 'collector', target_id: new collector's id, details: aggregator_id + collector phone + name.
  • Option 2: new aggregator_activity table mirroring agent_activity. Larger scope, justifiable if there are other aggregator-side activity events to track. For pre-holiday MVP, Option 1 keeps scope tight.

If Option 1 is chosen, verify admin_audit_log doesn't enforce actor_type IN ('admin') — if it does, widen the constraint as part of this PR's migration scope. (Pre-flight check in the implementation prompt.)

Schema

No new tables. No migrations beyond the possible admin_audit_log.actor_type constraint widening if Option 1 needs it.

8. Locked decisions
  • Menu placement: Option C — Register Collector at #1 + inline at point-of-purchase. (Jojo 2026-04-25.)
  • Demoted to "More" sub-menu: Marketplace + My Stats. One extra dial for those features.
  • Register flow shape: mirror existing agent register-collector flow (server.js:3918) — same fields, same field order, same INSERT, same error handling.
  • Default PIN: '0000' scrypt-hashed, must_change_pin: true. Same as agent flow.
  • City picker: reuse USSD_CITIES_LIST from PR #63 (8 capitals, paginated 3-per-page).
  • Inline path bridges back: after registration, prompt to continue the purchase the aggregator was originally trying to log (B7 screen). No re-dialling.
  • No SMS to the new collector on registration. In-person handoff of default PIN, same as agent pattern. Re-evaluate post-pilot if onboarding friction surfaces.
  • Audit trail: log to admin_audit_log with actor_type = 'aggregator'. Verify the constraint allows it; widen if needed in the same migration.
9. Verified vs Assumed

Verified against current main (prod tip 02d162b)

  • Aggregator USSD menu at server.js:3242 is currently 1. Log Transaction / 2. Pending Drop-offs / 3. Marketplace / 4. My Stats / 0. Exit.
  • Agent register-collector flow at server.js:3918 — signature handleAgentRegister(m, agent, prefilledPhone). Two paths (with/without pre-fill), 5/4 depth respectively. INSERT to collectors with default PIN 0000 + must_change_pin true.
  • USSD_CITIES_LIST at server.js:2417 — 8 pilot capitals with paginated picker via 9. More.
  • normalizeGhanaPhone() exists and is used in the agent flow.
  • collectors.phone has a unique constraint (errcode 23505 on duplicate).
  • admin_audit_log exists (added in PR #58 account-recovery series).

Assumed (verify during implementation prompt drafting)

  • admin_audit_log.actor_type column constraint. Need to confirm whether it's VARCHAR (any string) or has a CHECK / enum restricting to 'admin'. If restricted, the implementation either widens it or falls back to Option 2 (new aggregator_activity table). Resolved by reading the migration that created the table.
  • Aggregator purchase flow phone-lookup branch. Confirmed handleAggregatorPurchase-style function exists around server.js:3380, but the exact pattern for handling "phone not found" needs to be read before inserting the B2 branch. Currently it likely does an END with "not found, dial again."
  • Inline path's "drop back into purchase flow with collector pre-selected" — the purchase flow currently expects a phone-lookup at depth 1. After registration we have the collector_id directly. The cleanest implementation passes the collector_id forward via session state OR re-derives it from the phone lookup (now succeeds). Either works; verify the simpler path during implementation.

Could be wrong if

  • The admin_audit_log.actor_type is enum-restricted and widening it has cascade effects on existing admin audit queries. Mitigation: pre-flight grep for queries that filter by actor_type; widen migration with care.
  • The "More" sub-menu introduces too much friction for Marketplace browsing — possible but unlikely given Marketplace usage is low-frequency at pilot scale. Re-evaluate if usage data shows aggregators avoiding the sub-menu.
  • Aggregators want to register collectors WITH a custom PIN (not the default 0000). The current pattern hardcodes 0000 + force-change; agreeable for pilot. Post-pilot may want optional PIN entry on register.
