0. Role Detection — How the handler routes
The POST /api/ussd handler must now identify whether the caller is a collector, aggregator, or agent. Lookup order: collectors → aggregators → agents. First match wins. Same phone in multiple tables → collector takes priority.
POST /api/ussdserver.js
Role Detection Logic
1. normalizeGhanaPhone(phone) 2. getPhoneVariants(normalized) 3. Query collectors WHERE phone=ANY(variants) → found? role='collector' 4. Query aggregators WHERE phone=ANY(variants) → found? role='aggregator' 5. Query agents WHERE phone=ANY(variants) → found? role='agent' 6. None found? → handleUnregisteredUssd() (registers as collector)
Collector priority: if same phone in both tables, collector flow runs. Agents checked last (sub-accounts under aggregators).

6. Infrastructure Changes (Migration + Handler)
ChangeDetails
Migration: ussd_sessions Add aggregator_id INTEGER REFERENCES aggregators(id) ON DELETE SET NULL and agent_id INTEGER REFERENCES agents(id) ON DELETE SET NULL. Keep existing collector_id as-is — no rename, no data loss.
POST /api/ussd handler After collector lookup fails, query aggregators table with same phone variants. If found, call handleAggregatorUssd(parts, aggregator). Log aggregator_id in ussd_sessions INSERT.
Aggregator web login bug Line 3287: WHERE phone=$1 AND pin=$2 does plaintext comparison. Change to fetch by phone only, then verifyPassword(pin, row.pin). Same pattern as collector login. Otherwise new registrations (with hashed PINs) can't log in via web.
handleAggregatorUssd() New function ~120 lines. PIN retry (same pattern as collector), 3 menu options, aggregator-specific SQL queries.
